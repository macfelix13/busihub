# Busihub — Deployment & Environment Setup

## A note on how this codebase was built

This foundation was written in a sandboxed cloud environment whose network
access is restricted to a short allowlist of hosts (GitHub, the Anthropic
API, and a few others) — it explicitly blocks the npm and pip package
registries. Practically, that meant:

- Every file — including `package.json`'s dependency versions — was written by hand, not generated by scaffolding tools (`create-next-app`, `supabase init`). `npm install` was later run for real, but from the developer's own machine, not this sandbox — see `docs/SECURITY.md` for what that surfaced (a critical Next.js advisory in the initial hand-picked version, resolved by upgrading to Next 16 + ESLint 9 flat config) and what's still open.
- **The SQL migrations and RLS policies are the exception: they were genuinely executed and tested**, against a local PostgreSQL 16 instance in that same sandbox, standing in for Supabase (see `tests/db-harness/00_stub_supabase.sql` and `tests/security/tenant_isolation_and_rbac.sql`). Those results are real, not aspirational.
- `npm run build`, `npm run lint`, `npm run typecheck`, and `npm test` have **not** been run in this environment. They run automatically in `.github/workflows/ci.yml` on every push, where GitHub's runners have normal internet access — check that workflow's status on the repository before trusting that the frontend code compiles cleanly. If it doesn't on the first push, that's expected friction from hand-written dependency versions, not a sign anything deeper is wrong — check the CI log and fix versions/imports as flagged.
- **This sandbox cannot reach the real Supabase project directly**, confirmed two ways: the direct DB host (`db.<ref>.supabase.co`) only resolves via IPv6 and this container has no IPv6 stack at all; the IPv4 session-pooler host resolves fine over DNS but a raw TCP connect to it times out, meaning this environment's egress is restricted to a small host allowlist regardless of IP version — not an IPv6-specific gap. So migrations against the real project run in CI instead (`deploy-migrations` job, below), on GitHub's unrestricted runners, rather than from here.

## First-time setup

1. **Create a Supabase project** at supabase.com. Note the project URL, anon key, and service role key (Project Settings → API), and the direct database connection string (Project Settings → Database → Connection string → "Direct connection", not the pooled one).
2. **Copy environment variables**: `cp .env.example .env.local` and fill in the Supabase values plus `PIN_SESSION_SECRET` (`openssl rand -base64 48`). Paystack keys can wait until the payments phase.
3. **Install dependencies**: `npm install`.
4. **Run migrations**: `npm run db:migrate` — applies everything in `supabase/migrations/` in order, tracked in a `schema_migrations` table so it's safe to re-run.
5. **(Optional) load dev seed data**: `npm run db:seed` — creates a demo business and a demo login (`owner@busihub.dev.example` / `DevPassword123!`). Refuses to run against a connection string that doesn't look like a dev project without explicit confirmation. Never run against production.
6. **Regenerate real TypeScript types** now that a project exists, replacing the placeholder in `lib/supabase/database.types.ts`:
   ```bash
   npx supabase gen types typescript --project-id <your-project-ref> > lib/supabase/database.types.ts
   ```
7. **Run the dev server**: `npm run dev`, visit `/register`.

## Deploying

- **Frontend**: Vercel. Connect the GitHub repo, set the same environment variables from `.env.local` in the Vercel project settings (Production + Preview as appropriate), excluding `SUPABASE_DB_URL` (only needed for the migration/seed scripts, not the running app).
- **Database**: Supabase project created above. Run `npm run db:migrate` against it (from CI or locally) as part of your deploy process — this repo does not yet include an automated "migrate on deploy" step; add one deliberately once there's a real staging/production split to be careful about (Section 43).
- **Environment separation**: use separate Supabase projects for development, staging, and production — never point a local `.env.local` at a production project, and note `scripts/db-seed.mjs`'s guard against exactly that mistake.

## Backups & recovery (Section 42)

Supabase's paid plans include automated daily backups and point-in-time
recovery (plan-dependent — check the current tier's specifics on the
Supabase dashboard before relying on a specific RPO/RTO). This is **not**
automatic on the free tier. Whatever plan is used, treat Supabase's backup
coverage as the starting point, not the whole answer: document (and
periodically test) an actual restore procedure once a production project
exists, and decide an audit-log retention policy explicitly rather than
assuming "Supabase handles it."

## CI

`.github/workflows/ci.yml` has three jobs:

- `database`: spins up a throwaway Postgres service container, applies the auth/role stub + every migration + seed data, then runs `tests/security/tenant_isolation_and_rbac.sql` as a pass/fail gate.
- `app`: `npm ci`, typecheck, lint, unit/integration tests, `next build` — using placeholder env vars sufficient to build (no real Supabase/Paystack project is needed to pass this job).
- `deploy-migrations`: runs only on a push to `main`, only if the `SUPABASE_DB_URL` repository secret is set (otherwise it logs a warning and skips — it never fails the build for a missing secret). Applies `supabase/migrations/` to the real project via `npm run db:migrate`.

To enable `deploy-migrations`: repository **Settings → Secrets and variables → Actions → New repository secret**, name `SUPABASE_DB_URL`, value the **session pooler** connection string from Supabase (Project Settings → Database → Connection string → Session pooler — not the direct connection, which is IPv6-only and unreachable from plenty of CI/hosting environments, and not the transaction-mode pooler on port 6543, which doesn't reliably support the multi-statement DDL transactions these migrations use).

**Change the database password before relying on this in anything beyond local development.** A short dictionary-word password is fine for poking at a throwaway project, not for one with real data — rotate it from the Supabase dashboard (Project Settings → Database → Reset database password) and update the secret/`.env.local` to match.
